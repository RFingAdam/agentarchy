# Phase 2 — Theme engine and the asset audit: Implementation Plan

Spec: `docs/superpowers/specs/2026-08-22-agentarchy-design.md` (Phase 2 section, and the theming table at
"Plasma colour scheme" / "Light/dark" / "Wallpaper / lock / SDDM" / "Ghostty / Konsole"). The spec is binding;
this plan is its argument.

Phase 1 shipped one theme applied through a deliberately minimal `oal-theme-set-kde`: a colour scheme, a Konsole
scheme, and a wallpaper for the running session. Phase 2 makes that the whole surface — every theme, every
consumer, both directions of light/dark — and settles the question the repository is currently public with
unanswered: where 68 wallpapers came from and whether we may ship them.

## Global constraints

1. **No vendored file is hand-edited.** Changes to `upstream/VENDORED-FILES.txt` paths go through
   `bin/oal-dev-upstream-patch`; `bin/oal-dev-sync-upstream --check` stays clean at every commit.
2. **`bin/oal-dev-check` is 7 PASS at every commit.** New tests are bats under `test/unit`.
3. **The VM is the proof.** `test/vm/golden-path` must still pass at the end of the phase, extended with the
   theme assertions from Task 6.
4. **Generation is offline and pure; application talks to a session.** The split Phase 1 established stays: every
   generator is testable with `--dry-run --out`, and a missing Plasma tool degrades to a warning.
5. **Nothing in this phase depends on the layout work.** Phase 3 owns panels (default `ubuntu`, decided
   2026-08-23). A theme must look right on either layout.

## Verified facts (established, do not re-derive)

* `oal-theme-color --file <colors.toml> --all` resolves the full palette for any theme, including `color0`-`color15`
  and the light/dark `mode`. Every consumer must use it rather than parsing TOML again.
* `bin/oal-theme-set-templates` renders **every** `default/themed/*.tpl` into the staged theme directory with a
  generic loop; adding a template needs no patch to the vendored renderer.
* `default/themed/` already carries 14 agnostic templates including `ghostty.conf.tpl`. Konsole and Plasma are the
  two that do not exist, because upstream has neither.
* `plasma-apply-colorscheme` writes the scheme's colours *into* kdeglobals. With no session, the colours have to be
  seeded key by key (Phase 1, `oal-theme-set-kde`) or the desktop renders stock Breeze while claiming otherwise.
* 68 wallpapers across 22 themes, 51 MB, every one `UNAUDITED` in `NOTICE`. The repository went public on
  2026-08-23 with the audit pending, and git history is permanent.
* Upstream provenance is traceable: `basecamp/omarchy` is a public repo, and a blobless clone
  (`git clone --filter=blob:none`) gives `git log --follow --diff-filter=A` per file without pulling 51 MB of
  images. The GitHub API's `?path=` does not follow renames, and the wallpapers have been renamed at least once
  ("Named for direct selection", c254f890), so the clone is the reliable route.

## Task 1: Trace where every asset came from

**Files:** create `docs/asset-audit.md`; create `bin/oal-dev-asset-provenance` (dev tooling, native).

The audit is evidence, not opinion, so it is generated by a script that can be re-run when `upstream/PIN` moves.
For each `themes/*/backgrounds/*` and each `applications/icons/*`: first commit that added it (following renames),
date, author, the commit subject, and the PR body if the commit came from one. Output a table plus a per-file
verdict of `DOCUMENTED` (a source and licence are stated somewhere in that trail), `UNDOCUMENTED`, or `GENERATED`
(ours). Rate limit is 5000/h authenticated; the clone avoids most calls anyway.

Deliverable: `docs/asset-audit.md` with all 68 rows and a summary count, plus the icon table.

## Task 2: Act on the audit

**Files:** `themes/*/backgrounds/*`, `NOTICE`, `upstream/VENDOR-MANIFEST`, `tasks/todo.md`; create
`bin/oal-theme-bg-generate`.

Keep what is `DOCUMENTED`, with its source and licence in `NOTICE`. Everything `UNDOCUMENTED` leaves the tree.
A theme with no wallpapers is a broken theme, so the replacement is generated, not curated: a wallpaper rendered
from the theme's own `colors.toml` (ImageMagick, available in the base list), so every palette has at least one
background that is unambiguously ours. Curating CC0 photography is a later, optional pass.

`bin/oal-dev-notice-check` then gates on real provenance rather than the `UNAUDITED` placeholder.

**Owner-action, recorded not decided here:** deleting a file does not remove it from a public repository's history.
Whether to rewrite history (`git filter-repo` plus a force push, cheap while the repo is a day old and unforked)
or accept it is Adam's call, and it should be made *after* Task 1 says what is actually undocumented.

## Task 3: The generated files, as templates

**Files:** create `default/themed/plasma.colors.tpl`, `default/themed/konsole.colorscheme.tpl`; rewrite
`bin/oal-theme-set-kde` to consume them; `test/unit/theme-kde.bats`.

Phase 1's generator emits both files from bash. Moving them to templates puts them where every other themed config
lives, lets a user override one in `~/.config/oal/themed/`, and removes the second source of truth. The mapping is
unchanged (spec's theming table) and the existing bats assertions must keep passing across the move.

## Task 4: The rest of the theme surface

**Files:** patches to `bin/oal-theme-set` (KDE hook), `bin/oal-theme-set-kde`, `etc/sddm.conf.d/`,
`default/sddm/oal/`; possibly `bin/oal-theme-set-lock`.

Wire the consumers Phase 1 left: the SDDM greeter theme (`oal-refresh-sddm` already copies it; give it the palette),
the lock screen (`kscreenlockerrc` Greeter wallpaper), the icon theme from `themes/*/icons.theme`, and light/dark so
`mode = "light"` produces a light desktop rather than a light palette on a dark shell. `oal-theme-set` is vendored
and Hyprland-shaped: audit its 15 `post_theme_commands`, port what applies to KDE, exclude what does not, and record
each decision — this is the same "port or drop" ruling Phase 1 made for the channel cluster.

## Task 5: Every theme, tested

**Files:** create `test/unit/themes.bats`, `test/fixtures/themes/`.

Snapshot test: for all 22 themes, generate into a temp dir and compare against a committed fixture. A palette change
then shows up as a diff instead of a surprise. Plus the structural assertions that already exist, run across all 22
rather than tokyo-night alone, and a light-theme case (`white`, `catppuccin-latte`, `flexoki-light`).

## Task 6: Prove it in the VM

**Files:** `test/vm/assertions.sh`, `test/vm/golden-path`.

Cycle three themes in the live session (`tokyo-night` → `gruvbox` → `catppuccin-latte`, the last one light) and after
each: `kdeglobals` ColorScheme *and* its colours, the wallpaper path, the Konsole scheme, the icon theme. Screenshot
each. The screenshots are the deliverable — Phase 1's Task 6 proved that every assertion can pass while the desktop
still looks wrong.

## Verification (end-to-end)

1. `bin/oal-dev-check` — 7 gates.
2. `test/vm/golden-path` — green, with the Task 6 theme cycle included.
3. `docs/asset-audit.md` accounts for every file in `themes/*/backgrounds/` and `applications/icons/`, and `NOTICE`
   carries no `UNAUDITED` row.
4. Human check: Adam looks at the three theme screenshots.

## Out of scope for Phase 2

Panels and layouts (Phase 3), the OAL menu (Phase 3), `oal-update`/migrations (Phase 4), the agent layer (Phase 5),
the ISO (Phase 6). Curated photographic wallpapers beyond what the audit clears: optional, later, and never a
blocker for v0.1.0.
